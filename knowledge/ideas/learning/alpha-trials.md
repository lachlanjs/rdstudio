# Summary

Once an alpha exists, the developer will test it personally on four subjects
that differ in who draws the map, whether the territory can be checked
automatically, and how the knowledge is structured.

| Trial | Subject | What it tests |
|---|---|---|
| New codebase | an unfamiliar codebase; suggestion: **papis**, which the developer already uses, is mid-sized Python, and has a real purpose to learn it for | AI-drawn map of a territory that can be checked; staleness when code changes; catching up |
| Thesis | **himode** | the developer as the expert and main cartographer; nested and cross-scale links in their own research; payoff for writing up |
| Mathematics | **differential geometry** | a strongly prerequisite-ordered subject; reading order and pathfinding; exercises and problem-solving over recall; KaTeX rendering |
| Outside expertise | **music theory (harmony)**, the developer's choice | a subject that is partly a skill (hearing, playing) as well as knowledge, with nested structure (intervals, chords, progressions, form) and no code: whether the model generalises beyond technical work, and where it stops |

Immunology was also suggested (nomenclature-heavy, clearly nested scales) and
remains an option.

# Per trial

- Keep a short log (dates, what was done, what felt forced).
- Before starting, write down what you expect to be able to explain; check it
  after a few weeks, ideally with explain-back exercises the tool did not set.
- Note which features were used unprompted and which were ignored; use the
  [PID feature map](/ideas/learning/pid-feature-map.md) to see which parts of
  the loop were exercised.
